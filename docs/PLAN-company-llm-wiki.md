# 사내 LLM Wiki 개발 목표 플랜

작성일: 2026-10-02 · 방식: ruflo 구현 루프(Recall → Inspect → Route → Plan → Execute → Test → Validate → Receipt → Handoff) + Karpathy LLM Wiki 패턴

## 1. 목표

회사에서 생성되는 문서·회의록·문제점 리스트·해결 내용·메일을 한 곳에 넣으면, LLM이 이를 **연관된 것끼리 묶인 위키 문서(Markdown)** 로 계속 컴파일/갱신하고, 구성원이 **자연어로 질문하면 위키 근거로 답변**하는 사내 지식창고.

### 비기능 요구사항 (필수 조건)
| 요구 | 의미 |
|---|---|
| 인증/권한 | 로그인 사용자 식별, 권한 있는 사람만 접속·열람 |
| 사내망 전용 | 인터넷 노출 없음, 외부로 데이터 유출 경로 없음 |
| 다중 동시 사용자 | 중앙 서버 1대(또는 소수)에서 여러 명 동시 접속 |
| 점점 똑똑해짐 | 새 자료 투입 시 기존 문서 병합·교차 갱신(Karpathy의 compile/cascade) |
| Obsidian 호환 | 결과물은 `[[링크]]`가 있는 일반 Markdown vault로 열람 가능 |

## 2. 핵심 설계 결정

### 2.1 아키텍처
```
[사용자] ── 사내망/HTTPS ──> [리버스 프록시(TLS)]
                               ├─ Web UI (질문/검색/문서 열람, Obsidian식 링크·그래프)
                               └─ API 서버 ── SSO(OIDC/LDAP/AD) 인증
                                    ├─ AuthZ(RBAC/ACL) 미들웨어  ← 모든 읽기/검색/답변 앞단
                                    ├─ Ingest 워커(큐): 파싱 → raw/ 저장 → triage → compile → cascade
                                    ├─ Query 서비스: ACL 필터 검색 → LLM 답변 + 출처 인용
                                    └─ 저장소: raw/(불변 원본) · wiki/(MD vault, git 이력) · DB(메타/ACL/감사로그/벡터·BM25)
                               └─ LLM 추론 서버(사내 호스팅, 외부망 차단)
```
- **Obsidian의 역할**: Obsidian 자체는 단일 사용자 로컬 앱이라 인증/동시접속 기능이 없음. → 서버의 `wiki/` 폴더를 Obsidian 호환 vault 형식으로 유지하고, 다중 사용자 접근은 **웹 서버가 담당**. 필요 시 관리자/편집자는 vault를 Obsidian으로 열 수 있음(읽기 전용 배포 권장).
- **Karpathy 구조 채택**: `raw/`(원본, 수정 금지) → `wiki/<topic>/<article>.md`(컴파일 결과) + `index.md`, `log.md`. 근거 원칙(Grounding Invariant): 위키의 숫자·날짜·인용은 링크된 raw에 그대로 존재해야 함 → 린트로 검증.

### 2.2 가장 큰 리스크: 권한 누수 (설계 1순위)
LLM이 여러 자료를 합쳐 하나의 문서로 만들면, **A팀 기밀 + B팀 공개 자료가 한 문서에 섞여** 권한 우회가 생김. 대응:
1. 모든 raw 파일은 **ACL 라벨**(space/부서/프로젝트/등급)을 가짐 (폴더 또는 메타데이터로 부여).
2. 위키 문서의 ACL = **출처 raw들의 ACL 중 가장 제한적인 것**(교집합). 출처가 추가되면 ACL 재계산.
3. **컴파일 단위를 space로 격리**: 기본은 space 내부에서만 병합. space 간 교차 연결은 "공개 등급" 문서만 허용.
4. **검색 단계에서 ACL 필터 선적용** 후에만 LLM 컨텍스트에 투입(LLM에게 권한 판단을 맡기지 않음).
5. 인용 링크 클릭 시에도 서버가 재검증. 메일은 기본 비공개(수신자/참조자 기반 ACL).

### 2.4 확정 조건에서 나온 설계 주의점
1. **Windows에서 LLM 서빙**: vLLM은 Windows 네이티브를 공식 지원하지 않음. 선택지는 (a) WSL2/Docker + vLLM(동시 요청 배치 처리에 유리, 권장), (b) llama.cpp server 또는 Ollama Windows 네이티브(단순, 동시 처리 효율은 낮음). Phase 0에서 PoC 후 확정. 가능하면 서버 OS를 Linux로 할 수 있는지도 IT와 확인(어렵다면 WSL2 경로).
2. **개발 5GB ↔ 운영 48GB 격차**: 개발 GPU에서는 3~4B급 양자화 모델만 가능해 **답변 품질을 개발 환경에서 검증할 수 없음**. 위키 컴파일·답변 품질 평가(Phase 2)는 48GB 장비에서 해야 하므로, 서버 조기 반입 또는 임시 48GB 장비 확보 일정을 Phase 2 이전에 잡아야 함. 개발 단계는 모델을 교체 가능한 인터페이스(OpenAI 호환 API)로 만들어 파이프라인/권한/UI 위주로 진행.
3. **동시 80명 ≠ LLM 동시 80요청**: 질문 응답은 우선순위 큐, 인제스트(컴파일)는 백그라운드 저우선순위로 분리해 질문 지연을 보호. 48GB 모델 크기(대략 30B급 양자화 등)와 목표 응답시간은 Phase 0 벤치마크로 결정. 임베딩 모델은 별도 소형 모델로 분리.
4. **AD 권한 매핑**: 로그인 시 AD의 `department`/`memberOf`로 space 접근 결정. 그룹 변경(전보·퇴사) 반영을 위해 권한 캐시 TTL을 짧게 두고 주기 동기화. 파트 세분화는 AD 그룹 또는 OU 하위 단위를 space로 추가하는 방식 → 코드 변경 없이 설정으로 추가 가능하게 설계.
5. **부서 한정이라도 파트 격리는 유효**: 부서 내에서도 파트별 비공개 자료가 생기면 2.2의 교집합 규칙이 그대로 적용됨(부서 공용 space + 파트 space 계층).
6. **메일(EML)**: 기본 파트/부서 space 귀속, 수신자·참조자에 없는 사람에게는 노출하지 않는 옵션 제공(Phase 3에서 정책 결정 필요).

### 2.5 개발 방식: 사외 개발 → 사내 clone 후 인증 연동
IT 확인이 지금 불가능하므로, 인증 연동은 사내에서 직접 이어서 개발한다. 이를 위해 **사외 개발 단계에서 아래를 반드시 만들어 둔다**(나중에 끼워 넣기 어려운 부분):

1. **인증 교체 지점(AuthProvider 인터페이스)**: 모든 요청은 "현재 사용자 = {id, 이름, 부서, 파트, 그룹 목록}" 객체 하나로만 인증을 소비. 사외에서는 **개발용 가짜 로그인(dev stub)** 으로 사용자를 선택·전환, 사내에서는 SAML 구현으로 교체. 가짜 로그인은 운영 설정에서 **강제 비활성화**(환경 플래그 + 시작 시 검증).
2. **권한 강제 구조를 처음부터 내장**: 문서 접근, 검색, LLM 컨텍스트 구성, 인용 링크가 전부 "현재 사용자 + space ACL" 필터를 거치도록 데이터 모델(`space`, 문서/raw ACL 필드)을 Phase 1부터 포함. 나중에 덧붙이면 검색 인덱스와 위키 문서를 재설계해야 하므로 이 부분은 미루지 않는다.
3. **감사 로그 인터페이스**: 누가·언제·무엇을 조회/질문/수정했는지 한 곳으로 기록하는 함수와 테이블을 미리 마련(dev stub 사용자로도 기록됨). 사내에서는 사용자 식별만 실제 값으로 바뀜.
4. **space ↔ AD 매핑을 설정 파일로 분리**: 예) `부서/파트 이름 → space`, `그룹명 → 역할`. AD 구조가 확인되면 코드 수정 없이 설정만 채움.
5. **사내 반입(clone) 가능성**: 사내망이 인터넷에 막혀 있을 수 있으므로 (a) 모든 경로·주소·모델명은 환경설정으로 분리(하드코딩 금지), (b) 의존 패키지는 오프라인 설치 가능하도록 목록 고정(lock 파일) 및 반입용 패키지 묶음 절차 문서화, (c) LLM·OCR·임베딩 모델 파일 반입 절차 문서화, (d) 실행 명령 하나로 기동·초기화되는 스크립트와 점검 항목(README).
6. **권한 테스트는 사외에서 완료**: dev stub로 "A 부서 사용자가 B 부서 문서를 검색·질의·인용으로 볼 수 없다"는 침투 테스트를 사외에서 통과시켜 두고, 사내에서는 SAML 연결 후 동일 테스트를 재실행.

## 3. 단계별 개발 목표 (Phase)

### Phase 0 — 요구 확정 & 위협 모델 (1주)
- 남은 미정 사항(Q4 HWP/OCR, Q7 PII) 확정, 권한 모델·데이터 분류 정의, 위협 모델(권한 우회, 프롬프트 인젝션, 데이터 반출).
- LLM 서빙 PoC(Windows: WSL2+vLLM vs llama.cpp/Ollama), AD 연동 방식(LDAPS vs AD FS) 확정, 48GB 장비 확보 일정 수립.
- **완료 기준**: 결정 사항 ADR 작성, 인프라 사양 확정, 개발→운영 모델 교체 절차 합의.

### Phase 1 — 코어 위키 엔진 (단일 사용자, CLI) (2~3주)
- Karpathy 루프 구현: Ingest(fetch → triage → compile → cascade) / Query / Lint, `raw/`·`wiki/`·`index.md`·`log.md`.
- 파서: md/txt/docx/pptx/xlsx/pdf (+ HWP는 Q4 결과에 따라), 회의록·이슈·메일(EML) 정규화.
- 메일 스레드 묶기·중복 제거, 문제점→해결 내용 연결 문서 템플릿.
- 근거 검증 린트(raw 대비 숫자/날짜/인용 일치).
- **완료 기준**: 샘플 100건 인제스트 시 연관 문서 병합·상호 링크 생성, 린트 근거 불일치 0건, Obsidian에서 vault 정상 열람.

### Phase 2 — 검색 & 자연어 답변 (2주)
- 하이브리드 검색(BM25 + 임베딩, **한국어 형태소/토크나이저** 고려), 위키 우선·raw 보조 검색.
- 답변 시 출처 문서 인용 필수, 근거 없으면 "모른다" 응답.
- 평가셋(질문 30~50개) 구축 → 정답률/인용 정확도 측정 기준선.
- **완료 기준**: 평가셋 목표 정확도 달성(기준은 Phase 0에서 합의), 환각 인용 0건.

### Phase 3 — 인증·권한·감사 (3주) ★핵심
> **개발 분담**: 3-A(사외 개발, Phase 1~2와 병행)는 인증 교체 지점·권한 강제 구조·감사 로그 인터페이스를 만들고, 3-B(사내 clone 후 직접 개발)는 SAML 로그인과 AD 속성 매핑을 연결. 상세는 2.5절.
- SAML 2.0 SSO 로그인, 세션/토큰 관리, 역할(관리자/편집자/열람자) + space ACL.
- 2.2의 ACL 전파·교집합 계산, 검색/답변/링크 전 구간 서버측 강제.
- 감사 로그(누가 언제 무엇을 조회/질문/수정), 관리자 권한 관리 화면.
- **완료 기준**: 권한 침투 테스트 통과 — 무권한 사용자가 (a) 문서 직접 접근, (b) 검색 결과, (c) 챗 답변 내용, (d) 인용 링크, (e) 프롬프트 인젝션으로 우회, 모두 차단.

### Phase 4 — 다중 사용자 서버화 & 사내망 전용 배포 (2주)
- 웹 UI(질문창, 문서 뷰어, 백링크/그래프, 업로드), 인제스트 비동기 큐·워커(동시 인제스트 시 `index/log` 직렬화 락).
- 사내망 바인딩, TLS(사내 CA), 아웃바운드 차단(egress deny), 백업/복구, git 기반 위키 변경 이력과 롤백.
- 폴더 감시(저장폴더에 파일을 넣으면 자동 인제스트) + 실패 재시도.
- **완료 기준**: 동시 접속 N명 부하 테스트 통과, 외부 인터넷 차단 상태에서 전 기능 동작, 복구 리허설 성공.

### Phase 5 — 파일럿 & 품질 고도화 (3주~)
- 1개 팀 파일럿 → 피드백 → 주기적 린트(모순/오래된 주장 Outdated/Disputed 표기), 중복·고아 문서 정리 자동화.
- 이슈 해결 이력 기반 "유사 문제 추천", 메일 커넥터, 사용 통계.
- **완료 기준**: 파일럿 사용자 만족도·질문 해결률 목표 달성 후 전사 확대 결정.

## 4. 권장 기술 스택 (초안, Phase 0에서 확정)
- 백엔드: Python(FastAPI) 또는 Node(TypeScript) — 파서/ML 생태계상 Python 권장
- 저장: PostgreSQL(+pgvector, 전문검색) + 파일시스템(raw/wiki, git)
- 인증: SAML 2.0(AD FS 연동), 세션은 서버측 검증. 사용자 인증 로그인은 서버가 직접 비밀번호를 다루지 않음
- LLM: 사내 호스팅 오픈 모델(OpenAI 호환 API로 추상화). 운영 48GB급은 vLLM(WSL2/Docker) 우선 검토, 개발 5GB는 3~4B 양자화 모델. 한국어 성능 비교 후 모델 확정. 임베딩 모델도 사내 호스팅
- 프론트: 경량 웹앱(React/Vue 등), Markdown 렌더 + `[[wikilink]]` 지원
- 배포: Docker Compose(단일 서버) → 필요 시 확장

## 5. ruflo 실행 계획

> 이 절은 위키를 **개발하는 방법**(개발 도구 운영)이며, 제품 기능과는 무관합니다. 요약: 단계마다 소수의 에이전트가 격리된 작업공간에서 구현·테스트·보안 검토를 분담.

### 투입 에이전트/토폴로지 (hierarchical, 최대 8)
| 역할 | 에이전트 | 담당 Phase |
|---|---|---|
| 총괄·통합 | hierarchical-coordinator (리드=통합 오너, 공용 매니페스트/락파일 편집 전담) | 전체 |
| 요구/설계 | specification, system-architect, security-architect | 0, 3 |
| 위키 엔진 | coder ×2 (ingest/compile, query/search) | 1, 2 |
| 인증/권한 | backend-dev + security-auditor | 3 |
| 품질 | tester, reviewer | 전 단계 |
| 성능/배포 | performance-engineer | 4 |

### 운영 규칙
- 쓰기 에이전트마다 **격리 worktree + 파일 소유권 분리**(한 worktree에 두 writer 금지). 읽기 전용 리서치만 병렬.
- Phase별로 `task_create`로 수락 기준 등록 → 완료 시 테스트/보안 검증 결과를 `memory_store`(namespace `patterns`)에 기록, 다음 작업은 `memory_search`로 재사용.
- 보안 변경 후 `audit` 워커, 기능 추가 후 `testgaps` 워커 디스패치.
- 외부 배포/공개는 별도 승인 게이트 (사내 서버 배포도 사용자 승인 후).
- 시작 명령(승인 후): `npx @claude-flow/cli@latest swarm init --topology hierarchical --max-agents 8 --strategy specialized`
