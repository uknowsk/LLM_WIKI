작성일: 2026-10-02 · 환경: LM Studio `google/gemma-4-e4b`(채팅, 로드된 컨텍스트 8,192토큰) + `text-embedding-bge-m3`(임베딩) · 문서: 합성 코퍼스 61개 파일(위키 문서 47개) · 질문: 합성 100문항(조정 70 / 검증 30)

> **먼저 읽을 것**: 이 수치는 **합성 문서 + 소형 모델** 기준입니다. 절대 점수는 실제 사내 문서에서 더 낮게 나올 가능성이 큽니다. 믿을 수 있는 것은 "어떤 설정이 상대적으로 낫다"는 순서와, 평가 체계 자체(재현·유출 검사·검증 분리)입니다. 사내(Gauss)에서 반드시 다시 조정하세요(6절).

## 2. 평가 방법

- **정답 판정**: 정답 핵심 사실(숫자·날짜·고유명사)이 답변에 모두 들어 있으면 정답. 숫자는 `1200만원 = 1,200만원`, 날짜는 `2026년 9월 30일 = 2026-09-30`처럼 정규화해서 비교합니다.
- **거절 판정**: "답 없음"·"타 부서" 질문은 `근거 없음`으로 답해야 정답입니다.
- **유출 판정**: 답변·출처·검색 결과에 다른 부서의 문서나 사실이 하나라도 있으면 *치명적 실패*로 따로 세며, 유출이 있는 설정은 점수와 무관하게 무효입니다.
- **종합 점수(생성 단계)**: 답변 정확도와 거절 정확도를 합산한 값(`python -m llmwiki.eval report`의 정의 참조).
- **과적합 방지**: 70문항으로만 조정하고, 30문항은 선택한 설정 하나를 **한 번만** 평가했습니다(같은 설정 재평가는 도구가 막습니다).

## 3. 단계별 결과

### 3.1 검색 단계 (LLM 없음, 조정 70문항)
- 기본 설정의 검색 목적함수: **0.6635** (정답 문서 포함률 98.2%, 그러나 답 없음·타 부서 질문에서 검색이 비는 비율 0%).
- 1차 탐색 최고 **0.7184**, 2차 탐색 최고 **0.8108** (의미 검색 전용, 코사인 하한 0.525).
- 코사인 하한은 0.5125 → 0.77, **0.525 → 0.81**, 0.5375 → 0.785로 안쪽에서 정점을 찍었습니다(탐색 범위 가장자리가 아님).
- **중요한 해석**: 이 점수의 상승은 "검색이 비어서 질문을 거절"하는 비율이 올라서 생긴 것입니다. 그 대가로 표현이 다른 질문(paraphrase)의 정답 문서 포함률이 100% → 81.8%로 떨어졌습니다. 즉 **검색 단계 점수만 보면 잘못된 결론**(의미 검색 전용 + 높은 하한)이 나옵니다.

### 3.2 생성 단계 (실제 LLM, 조정 70문항)
검색 후보 3종(A: 의미 전용 하한 0.525 / B: 의미 전용 하한 0.425 / C: 하이브리드)을 실제 답변으로 비교했습니다. LLM이 "근거 없음"으로 걸러 주기 때문에 **재현율이 높은 하이브리드(C)가 가장 좋았습니다.**

| 순위 | 후보 | temperature | Top_K | 문서당 | 종합 | 정답률 | 거절 | 출처 |
|---|---|---|---|---|---|---|---|---|
| 1 | C 하이브리드 | 0.3 | 8 | 2,000자 | **0.9618** | 94.6% | 100% | 96.4% |
| 2 | C | 0.0 | 8 | 제한 없음 | 0.9491 | 92.7% | 100% | 96.4% |
| 3 | C | 0.0 | 5 | 2,000자 | 0.9491 | 92.7% | 100% | 96.4% |
| 4 | C | 0.15 | 8 | 2,000자 | 0.9491 | 92.7% | 100% | 96.4% |
| 5 | B 의미 0.425 | 0.0 | 8 | 2,000자 | 0.9364 | 90.9% | 100% | 92.7% |
| … | A 의미 0.525 | 0.3 | 8 | 2,000자 | 0.9236 | | | |

파라미터 민감도(값별 최고 점수):
- **검색 후보**: C 0.9618 > B 0.9364 > A 0.9236 → 하이브리드가 우세.
- **Top_K**: 3 → 0.9364, 5 → 0.9491, **8 → 0.9618**. 많이 넣을수록 좋았습니다(컨텍스트 예산 안에서).
- **temperature**: 0.0 → 0.9491, 0.15 → 0.9491, 0.3 → 0.9618. **차이는 질문 1~2개 수준**이라 "temperature 0.3이 낫다"고 결론내리지 않습니다. 영향이 작다고 보는 것이 맞습니다.
- **문서당 길이 제한**: 없음 0.9491, 2,000자 0.9618. 역시 근소한 차이입니다.

## 4. 코드에 반영한 기본값

`src/llmwiki/engine/params.py`의 `RetrievalParams` 기본값을 **검색 파라미터만** 바꿨습니다.

| 파라미터 | 이전 | 현재 |
|---|---|---|
| top_k | 5 | **8** |
| candidate_pool | 50 | **20** |
| rrf_k | 60 | **30** |
| w_dense | 1.0 | **0.5** |
| bm25_k1 / bm25_b | 1.5 / 0.75 | **0.9 / 0.4** |
| retrieval_mode | hybrid | hybrid (그대로) |
| min_cosine | 0.0 | 0.0 (그대로: 3.1절 이유) |
| **temperature, max_context_chars** | None / 0 | **그대로 둠** |

`temperature`와 문서당 길이 제한은 `gemma-4-e4b`(8k 컨텍스트)에서만 찾은 값이고 효과도 작아서 바꾸지 않았습니다. 사내 Gauss(추론 모델, 64k 컨텍스트)에서는 다르게 동작할 수 있습니다.

**이 결정의 한계 (정직하게)**
- 조정용 점수가 동점이라 처음에는 "근거가 없으니 기본값을 그대로 둔다"고 정했고 실제로 되돌렸습니다. 그런 다음 검증 결과를 본 뒤(튜닝한 설정이 약 2문항 앞섬) **검색 기본값을 튜닝한 값으로 다시 바꿨습니다.** 즉 이 선택은 *검증 결과를 본 뒤의 사후 판단*이고, 검증 점수 0.909는 그만큼 약간 낙관적일 수 있습니다.
- 바꾼 근거: 조정용 동점, 검증용에서 낮지 않음, Top_K 증가가 여러 문서 종합에 유리하다는 메커니즘, Gauss의 64k 컨텍스트에서는 문서를 더 넣는 비용이 작음.
- 바꿔서 치르는 비용: 질문당 프롬프트가 길어져 응답이 조금 느려지고 토큰을 더 씁니다(컨텍스트 예산 안에서만 채워짐).
- **따라서 이 값은 "입증된 최적"이 아니라 "현재 가장 나은 추정"입니다.** 사내에서 실제 문서와 사람이 만든 질문으로 같은 절차를 다시 돌려 확정하세요(6절).

## 5. 알려진 한계와 아직 못 한 것

1. **합성 데이터**: 한 사람이 쓴 깔끔한 문서·질문입니다. 실제 문서의 오타, 표기 불일치, 긴 문서, OCR 잡음은 반영되지 않았습니다.
2. **소형 모델**: 4B급 모델 기준입니다. 더 큰 모델은 최적 설정이 다를 수 있습니다.
3. **표본 크기**: 조정 70, 검증 30. 유형별 검증은 2~5문항이라 통계적으로 약합니다. 동점에 가까운 설정이 여러 개입니다.
4. **하이브리드 검색은 스스로 거절하지 못합니다**: 키워드 검색은 항상 뭔가를 돌려주므로, 거절은 전적으로 LLM("근거 없음")에 의존합니다. 모델이 약하면 엉뚱한 답을 만들 위험이 있습니다. 개선 방향: 점수 하한(BM25·결합 점수) 도입.
5. **문서 만들기(컴파일) 단계 미평가**: 소형 모델이 판단을 못 하면 폴백(원문을 새 문서로)이 작동했습니다(로그에 `compile fallback`). 이 비율과 문서 품질은 정량 평가하지 않았습니다.
6. **정답 판정이 문자열 기반**: 같은 뜻의 다른 표기를 오답으로 처리할 수 있고, 짧은 정답(`22`, `41%`)은 우연히 맞을 수 있습니다.
7. **임베딩 모델 컨텍스트**: LM Studio에서 `bge-m3`가 2,048토큰으로 로드되어 있었습니다. 긴 문서는 임베딩이 잘리거나 실패해 키워드 검색으로만 쓰일 수 있습니다(로드 컨텍스트를 키우세요).
8. **검색 점수 해석**: 1단계 점수는 검색이 비는 비율을 보상해서 3.1절과 같은 착시가 있습니다. 설정 선택은 항상 생성 단계(실제 답변) 점수로 하세요.

## 6. 사내(Gauss)에서 다시 할 일

- **검색 파라미터는 그대로 시작해도 됩니다.** 임베딩이 같은 `bge-m3`이므로 코사인 분포와 검색 순위는 크게 달라지지 않을 가능성이 높습니다. 다만 코퍼스가 바뀌므로 실제 문서로 한 번 검증하세요.
- **생성 파라미터(temperature, Top_K, 문서당 길이)는 Gauss로 다시 조정하세요.** Gauss는 64k 컨텍스트라 Top_K를 더 크게 시험할 수 있고, 추론 모델이라 temperature 효과가 다를 수 있습니다.
- 절차: 실제 문서 일부와 사람이 만든 질문·정답 50~100개로 평가 세트를 만들고(`eval/qa.jsonl` 형식), `python -m llmwiki.eval build → eval → tune → final → report`를 순서대로 실행합니다. **검증 분할로는 절대 조정하지 마세요.** 유출은 0이어야 합니다.
- 자세한 명령과 환경변수는 `docs/ONSITE-HANDOFF.md`를 보세요.

## 7. 재현 방법

```
PYTHONPATH=src python -m llmwiki.eval build --corpus eval/corpus --out data/eval --llm-model google/gemma-4-e4b --base-url http://127.0.0.1:1234/v1
PYTHONPATH=src python -m llmwiki.eval tune --stage retrieval --data data/eval --qa eval/qa.jsonl --trials 300 --seed 0
PYTHONPATH=src python -m llmwiki.eval tune --stage generation --data data/eval --qa eval/qa.jsonl --from-results <후보 기록.jsonl> --top-n 3 --trials 18 --seed 2
PYTHONPATH=src python -m llmwiki.eval final --data data/eval --qa eval/qa.jsonl --config eval/results/best-generation.json
PYTHONPATH=src python -m llmwiki.eval report --results eval/results
```
시도 기록: `eval/results/tune-retrieval*.jsonl`, `tune-generation.jsonl`(14회), 최종 평가: `eval/results/final-bdba7d86c27d0d14.json`.
