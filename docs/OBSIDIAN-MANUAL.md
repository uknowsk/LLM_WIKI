# 사내 LLM 위키 사용 매뉴얼 — 옵시디언 설정 · 자료 입력 · 자연어 질문

대상: 관리자(위키 폴더를 옵시디언으로 보는 사람)와 자료를 넣는 담당자, 질문하는 일반 사용자.
상태 표시: **[검증]** = 이 저장소 개발 PC에서 실제로 실행·확인한 것 / **[미검증]** = 문서·코드 근거만 있고 직접 실행해 보지 못한 것.

---

## 0. 한눈에 보기

```
 자료(회의록·메일·엑셀·워드·PDF)
        │  ① 웹 "업로드" 탭   또는   ② inbox/<부서>/ 폴더에 복사
        ▼
 [파이프라인]  읽기 → (개인정보 마스킹 옵션) → raw/ 원본 저장 → LLM이 위키 문서로 정리 → 임베딩(검색용 벡터) 생성
        ▼
 raw/<부서>/…md        위키 문서  wiki/<주제>/…md   ←── 옵시디언(관리자)이 이 폴더를 "보는" 용도
        ▼
 [웹 화면]  질문 탭에 자연어로 질문 → 권한 있는 문서만 검색 → LLM이 근거 문서로 답변 + 출처 번호
```

세 가지만 기억하세요.

1. **옵시디언은 "보는 도구"입니다.** 로그인·권한·질문 답변은 모두 웹 서버가 합니다. 옵시디언은 로그인도 권한도 없습니다.
2. **위키 폴더(`wiki/`)에는 모든 부서의 문서가 섞여 있습니다.** 옵시디언으로 이 폴더를 열 수 있는 사람은 *전 부서 문서를 볼 수 있는 사람*입니다. 그래서 옵시디언 사용은 **관리자 전용**이고, 일반 사용자는 반드시 웹 화면을 쓰게 하세요. (부서별로 걸러서 내보내는 기능은 **아직 없습니다**.)
3. **위키 문서는 LLM이 만들고 갱신합니다.** 직접 고치면 다음 자료가 들어올 때 덮어써질 수 있습니다. 틀린 내용은 *정정 자료를 새로 넣는 방식*으로 고치세요(5절).

---

## 1. 폴더 구조 (데이터 위치)

기본 위치는 `WIKI_DATA_DIR`(미설정 시 실행 폴더의 `./data`)입니다. **[검증]** 실제 생성된 구조:

```
data/
├─ inbox/                 ← 자료를 넣는 곳
│   ├─ dept-a/            ←   부서(space)별 폴더. 폴더 이름 = 그 자료의 열람 권한 범위
│   ├─ dept-b/
│   ├─ _done/             ←   처리 완료 (마스킹 켠 부서는 원본이 지워지고 .processed.txt 표식만 남음)
│   ├─ _failed/           ←   3회 재시도 후 실패 (+ .reason.txt 에 이유)
│   └─ _rejected/         ←   형식·폴더 규칙 위반으로 거부 (+ .reason.txt)
├─ raw/                   ← 원본 사본(수정 금지). 위키 문서의 근거
│   └─ dept-a/2026-10-02-회의록-2026-09-30.md
├─ wiki/                  ← LLM이 만든 위키 문서  ★ 옵시디언이 여는 폴더
│   ├─ <주제>/<문서>.md           (부서 구분 없이 섞여 있음!)
│   ├─ <주제>/<문서>.md.bak       (갱신 직전 이전 버전 백업)
│   └─ _meta/<부서>/index.md, log.md   (부서별 목차와 처리 이력)
├─ wiki.db                ← 문서·출처·권한·임베딩·감사 기록 (SQLite)
└─ sessions.db            ← 로그인 세션 (웹)
```

- 문서의 **부서(권한)** 는 폴더가 아니라 `wiki.db`에 있습니다. 문서의 열람 범위 = 그 문서를 만든 *모든 출처 자료의 부서*를 전부 가진 사람. 두 부서 자료가 섞인 문서는 두 부서 모두 가진 사람만 봅니다.
- `data/`는 git에 올리지 않습니다(`.gitignore`). 백업은 `data/` 전체를 복사하세요(서버를 멈추거나 `wiki.db-wal`·`wiki.db-shm`까지 함께).

## 2. 옵시디언 설정 (관리자용)

> 옵시디언 화면 조작은 **[미검증]** 입니다(이 개발 PC에서 옵시디언을 실행해 확인하지 못했습니다). 메뉴 이름은 Obsidian 1.x 기준이며 버전에 따라 위치가 다를 수 있습니다. 위키 문서 *형식*은 실제 생성 파일로 **[검증]** 했습니다.

### 2-1. 설치와 반입
- 사내 소프트웨어 반입 절차를 따르세요. 옵시디언은 **업데이트 확인·Obsidian Sync·Publish·커뮤니티 플러그인**을 쓸 때만 외부와 통신합니다. **Sync와 Publish는 켜지 마세요**(문서가 사외로 나갑니다).
- 가능하면 자동 업데이트를 끄고(설정 → 일반/정보 영역의 "자동 업데이트"), 업데이트는 IT가 배포하는 버전만 쓰세요.

### 2-2. 보관소(Vault) 열기 — 어느 폴더를 열 것인가
| 선택 | 결과 | 권장 |
|---|---|---|
| **`data/wiki` 폴더를 Vault로** | 위키 문서 사이의 `[[링크]]`가 모두 동작. 문서 하단 `Sources`의 raw 링크(`../../raw/…`)는 Vault 밖이라 **깨져 보임**(정상) | **권장** |
| `data/` 전체를 Vault로 | raw 링크도 동작하지만 `inbox`(처리 전 원본)·`raw`·DB 파일까지 노출 | 비권장 |
| 네트워크 공유 폴더로 열기 | 가능하나 느리고 서버가 파일을 갱신하는 중에 열릴 수 있음 | 읽기 전용 공유 + 로컬 복사 권장 |

절차: 옵시디언 → "보관소 폴더 열기" → `…\data\wiki` 선택. 그러면 `wiki\.obsidian\` 설정 폴더가 생깁니다(git·백업에서 제외하세요). 이 폴더는 프로그램 동작에 영향을 주지 않습니다.

### 2-3. 권장 설정값
| 위치(설정 →) | 항목 | 값 | 이유 |
|---|---|---|---|
| 파일 및 링크 | 위키링크 사용 | **켬** | 문서가 `[[주제/문서\|제목]]` 형식 사용 |
| 파일 및 링크 | 새 링크 형식 | **보관소 기준 절대 경로** | 링크가 `주제/문서` 형태(보관소 루트 기준) |
| 파일 및 링크 | 모든 파일 확장자 감지 | **끔** | `.md.bak`(백업)이 목록에 나오지 않게 |
| 파일 및 링크 | 제외할 파일 | 필요 시 `_meta/` | 부서별 목차·처리 이력을 숨기고 싶을 때 |
| 편집기 | 기본 편집 모드 | **읽기 보기** | 실수로 문서를 고치지 않게 |
| 핵심 플러그인 | 백링크, 나가는 링크, 그래프 보기, 검색, 속성 보기, 태그 | **켬** | 탐색용 |
| 커뮤니티 플러그인 | 제한 모드 | **켬(기본)** | 사내 승인 없는 플러그인 차단 |

선택 사항: Dataview 플러그인(사내 승인 필요, 반입은 수동 설치). 예시(문서 목록을 최근 갱신순으로) **[미검증]**:

````
```dataview
TABLE updated AS 갱신일
FROM ""
WHERE updated >= "2026-10-01"
SORT updated DESC
```
````
`updated`는 따옴표 문자열(`"2026-10-01"`)이라 문자열 비교로 씁니다.

### 2-4. 문서 읽는 법 **[검증]**
실제 문서의 구조:

```
---
title: "2026년 3분기 장애 대응 현황 요약"        ← 제목(JSON 따옴표 형식)
updated: "2026-10-01"                              ← 마지막 갱신일(UTC 기준, 하루 차이 날 수 있음)
sources: ["raw/dept-a/2026-10-02-incident-status-2026q3.md", …]   ← 이 문서의 근거 원본(권한의 기준)
related: ["코어-스위치-…/장애-보고서-….md", …]      ← 같은 부서의 관련 문서
---
# 2026년 3분기 장애 대응 현황 요약
(본문: 표, 목록, 요약 …)

## Sources
- [2026-10-02-….md](../../raw/dept-a/….md)         ← 근거 원본 링크(Vault가 data/wiki면 깨져 보임)

## Related
- [[주제/문서|제목]]                                 ← 옵시디언에서 클릭해 이동 + 그래프에 연결선으로 표시
```
- **그래프 보기**: 관련 문서끼리 선으로 이어집니다. 연결이 많은 문서가 그 주제의 중심입니다.
- **백링크 패널**: 이 문서를 가리키는 문서 목록(예: 장애 보고서가 어느 요약에서 인용되는지).
- **`wiki/_meta/<부서>/index.md`**: 그 부서의 전체 문서 목차. **`log.md`**: 처리 이력 한 줄씩(`New`=새 문서, `Update`=기존 문서에 병합, `Disputed`=기존 내용과 충돌 표시, `fallback:…`=모델이 판단하지 못해 원문을 그대로 새 문서로 만듦).
- `*.md.bak`: 갱신 직전 버전. 필요하면 복구용으로만 쓰세요.

## 3. 자료 넣는 법

### 3-1. 두 가지 경로
**A. 웹 "업로드" 탭** (일반 담당자 권장 — 내 부서 폴더로만 올라갑니다) **[검증: 코드·자동 테스트]**
1. 로그인 → **업로드** 탭 → "공간"에서 내 부서 선택 → 파일 선택 → 업로드.
2. 업로드된 파일은 서버의 `inbox/<부서>/`에 쌓이고, 파이프라인이 자동 처리합니다.
3. 내가 속하지 않은 부서는 선택할 수 없고, 서버도 거부합니다.

**A-2. 웹 "메모" 탭** (파일을 만들 필요 없이 바로 적거나, 웹페이지에서 복사한 내용을 붙여 넣기) **[검증: 자동 테스트 + 브라우저(개발 모드, 합성 내용)로 저장·오류 문구·파일 생성 확인]**
1. 로그인 → **메모** 탭 → 공간 선택 → (제목, 출처 URL은 선택) 내용 입력 → 저장.
2. `inbox/<부서>/YYYY-MM-DD 제목.md` 로 저장되어 업로드와 같은 경로로 처리됩니다. 제목을 비우면 내용 첫 줄을 씁니다. 같은 제목이 있어도 덮어쓰지 않습니다.
3. **출처 URL 은 메모에 글자로만 기록하고 서버가 접속하지 않습니다**(외부 접속 금지 원칙). 페이지 내용은 직접 복사해서 붙여 넣으세요.
4. 한 번에 최대 1MiB(업로드 한도 이하). 제어문자는 제거되고, 제목의 경로 문자(`/ \ :` 등)는 공백으로 바뀝니다.
5. 이미지(png/jpg) 파일은 **업로드 탭/폴더 입력**으로 넣을 수 있습니다(OCR 설정이 있을 때만 글자를 읽습니다. 없으면 실패 안내 파일이 생깁니다). 메일 안의 이미지는 처리하지 않습니다.
6. 아직 안 되는 것: 메일/메신저 자동 수집(사내 자격증명 필요), 브라우저 확장 클리퍼, HWP.

**B. `inbox/<부서>/` 폴더에 직접 복사** (관리자·대량 입력)
- 예: `data\inbox\dept-a\2026-09-30-주간회의록.docx`
- **부서 폴더 밖(`inbox` 바로 아래)에 둔 파일은 처리하지 않고 `_rejected`로 보냅니다**(부서를 추측하지 않음).
- 복사 중인 파일은 다음 스캔(5초)까지 기다렸다가 처리합니다.

### 3-2. 부서(space) 이름 규칙 **[검증]**
- 소문자 영문·숫자·하이픈(`-`)만, 구분은 `/`(폴더 단계), 최대 4단계. 예: `dept-a`, `dept-a/part-1`.
- 대문자·공백·점·밑줄로 시작하는 이름(`_done` 등 예약)·Windows 예약어(`con`, `nul` …)는 거부됩니다.
- 부서를 파트로 쪼갤 때는 폴더만 추가하면 됩니다(`inbox/dept-a/part-1/`). **권한 매핑(AD 그룹 ↔ 부서 이름)은 사내 SAML 연결 때 설정**합니다.

### 3-3. 지원 형식과 규칙
| 형식 | 가능 | 규칙·주의 |
|---|---|---|
| `.md` `.txt` | O | UTF-8(실패 시 CP949). 첫 줄 `# 제목`을 권장 |
| `.docx` | O | 표의 **병합 셀**(가로·세로)을 펼쳐 읽음 **[검증]**. 텍스트 상자·머리글/바닥글·체크박스 포함. 표 안 표는 아래에 이어서 표시 |
| `.xlsx` | O | **병합 셀**을 펼침 **[검증]**. 날짜·퍼센트·천 단위는 *화면에 보이는 모양*으로 읽음. 수식은 계산하지 않고 **저장된 결과값**만 읽음 → *엑셀에서 저장한 뒤* 올리세요. 숨김 시트는 제외, 시트당 2만 셀·50시트까지 |
| `.eml` | O | 메일 1통 = 문서 1개. 첨부는 별도 문서로 같은 부서에 들어감 |
| `.pdf` | 부분 | 글자가 선택되는 PDF는 `pypdf` 설치 시 읽음. **스캔 PDF는 OCR 연결 전에는 실패**(`_failed`) |
| `.doc` `.xls` `.ppt(x)` `.hwp(x)` `.msg` | **X** | 구형·한글·Outlook 형식은 미지원 → `.docx`/`.xlsx`/`.pdf`로 저장해서 올리세요 |
- 파일당 기본 50MB 제한. 암호가 걸린 파일은 읽지 못합니다.
- **업로드 파일 이름**: 한글·영문·숫자·공백·`._-()[]`만 허용(경로 문자·`:`·제어문자·앞의 점 거부). 예: `회의록 (최종)_v2.md` O, `a/b.md` X.

### 3-4. 처리 흐름과 결과 확인 **[검증]**
| 단계 | 일어나는 일 | 어디서 확인 |
|---|---|---|
| 1 | 파일을 형식별로 읽어 텍스트로 변환(표는 마크다운 표) | — |
| 2 | (부서 정책이 켜져 있으면) 개인정보 마스킹 | `WIKI_PII_POLICY_FILE` |
| 3 | `raw/<부서>/날짜-이름.md` 로 원본 사본 저장(머리글 `> Source/Collected/Published`) | `raw/` |
| 4 | LLM이 기존 문서와 비교해 *새 문서 / 기존 문서 갱신 / 충돌 표시* 결정 → `wiki/<주제>/…md` 작성 | `wiki/`, `_meta/<부서>/log.md` |
| 5 | 검색용 임베딩 생성 | `wiki.db` |
| 6 | 원본을 `inbox/_done/`으로 이동 | `_done/` |
- 소요 시간: 소형 로컬 모델(4B)로 문서당 약 30~50초였습니다. 사내 Gauss는 달라질 수 있습니다 **[미검증]**.
- 실패하면 `_failed/<부서>/파일` 옆의 `.reason.txt`에 이유가 적힙니다. 같은 이름으로 다시 넣으면 재시도됩니다.
- 같은 내용을 같은 부서에 다시 넣으면 건너뜁니다(중복 방지). 다른 부서에는 따로 처리됩니다.
- **개인정보 마스킹을 켠 부서**: 처리가 끝나면 원본 파일은 **삭제**되고 마스킹된 텍스트만 남습니다. **원본은 반드시 본인이 따로 보관하세요.**

### 3-5. 공용 폴더(SMB 공유)로 넣기
직원이 웹 화면 없이 **네트워크 폴더에 파일만 끌어다 놓는** 방식입니다. 원칙: **부서는 폴더로만 정하고, 그 폴더에 누가 쓸 수 있는지는 Windows(NTFS/공유 권한 + AD 그룹)가 정합니다.** 파이프라인은 파일 내용·소유자·AI로 부서를 추측하지 않습니다.

**폴더 구조 예** (공유 `\\wiki-server\wiki-inbox` = 서버의 `<WIKI_DATA_DIR>\inbox`)
```
inbox\
  dept-hr\          인사팀 그룹만 쓰기      (별칭을 쓰면 인사팀\ 처럼 한글 이름도 가능, 아래 참고)
  dept-a\           A부서 그룹만 쓰기
  dept-a\part-1\    A부서 1파트 (필요할 때만)
  _done\ _rejected\ _failed\   관리자·서비스 계정 전용 (일반 직원에게는 보이지 않게)
```

**관리자 설정 레시피** **[미검증: 이 PC에서 실행하지 않음]** (관리자 PowerShell, 값은 사내 환경에 맞게 바꿈)
```powershell
$inbox = "D:\wiki-data\inbox"                  # = WIKI_DATA_DIR\inbox (서버 로컬 디스크)
$svc   = "CORP\svc-wiki"                       # 파이프라인 서비스 계정
$groups = @{ "dept-hr" = "CORP\wiki-hr"; "dept-a" = "CORP\wiki-a"; "dept-a\part-1" = "CORP\wiki-a-p1" }   # space 폴더 = AD 그룹
New-Item -ItemType Directory -Force $inbox, "$inbox\_done", "$inbox\_rejected", "$inbox\_failed" | Out-Null
foreach ($d in $groups.Keys) { New-Item -ItemType Directory -Force "$inbox\$d" | Out-Null }

# 1) 루트: 상속(넓은 그룹) 제거 -> SYSTEM/Administrators/서비스 계정만. 직원은 '이 폴더만' 읽기(목록 표시용)
icacls $inbox /inheritance:r
icacls $inbox /grant "SYSTEM:(OI)(CI)F" "BUILTIN\Administrators:(OI)(CI)F" "${svc}:(OI)(CI)M"
icacls $inbox /grant "NT AUTHORITY\Authenticated Users:(RX)"      # 상속 플래그 없음 = 루트에만 적용
# 2) 부서 폴더: 해당 AD 그룹에만 Modify (하위 폴더·파일에 상속)
foreach ($e in $groups.GetEnumerator()) { icacls "$inbox\$($e.Key)" /grant "$($e.Value):(OI)(CI)M" }
# 3) 공유: 접근 기반 열거(ABE) -> 각 팀에는 자기 폴더만 보임. 공유 권한은 넓게, 실제 제한은 NTFS 가 담당
New-SmbShare -Name "wiki-inbox" -Path $inbox -FolderEnumerationMode AccessBased `
  -FullAccess $svc, "BUILTIN\Administrators" -ChangeAccess "NT AUTHORITY\Authenticated Users"
icacls $inbox /t /c | Out-File .\inbox-acl-report.txt   # 적용 결과 확인(부서 폴더에 다른 부서 그룹이 없는지)
```
- 하위 폴더(`dept-a\part-1`)는 상속 때문에 `dept-a` 그룹도 쓸 수 있습니다. 파트를 분리하려면 그 폴더에서 `icacls "$inbox\dept-a\part-1" /inheritance:d` 후 필요한 그룹만 남기세요. 단, 위키 쪽 열람 권한은 정확한 space 이름 단위이므로 사용자 매핑(b-8)도 맞춰야 합니다.
- Modify 권한이라 같은 폴더 사용자끼리 서로의 파일을 지울 수 있습니다(쓰기 전용 "드롭박스"는 처리결과 메모를 못 읽어 권장하지 않음).
- 파이프라인 서비스 계정은 **inbox 전체에 Modify** 여야 `_done` 이동과 메모 작성이 됩니다. 확인: `scripts\run-doctor.ps1` 의 `inbox.layout`.

**직원이 하는 일**
1. 공유 폴더 안의 **내 부서 폴더**에 파일을 복사합니다. 형식을 바꾸려고 이름만 고치지 마세요(`.doc`를 `.docx`로 이름만 바꾸면 깨진 파일이 됩니다. 워드/엑셀에서 *다른 이름으로 저장*).
2. 약 1분 기다립니다(복사 중·열려 있는 파일은 다음 스캔으로 미룹니다).
3. 처리되면 파일이 **폴더에서 사라집니다**(관리자 영역 `_done`으로 이동). 사라지는 것이 정상입니다.
4. 처리하지 못했으면 같은 폴더에 `<파일이름>.처리결과.txt` 가 생깁니다. 사유(지원하지 않는 형식 / 파일이 손상됨 / 읽기 실패 / 처리 실패 등)와 조치가 한글로 적혀 있고, 파일 내용은 들어 있지 않습니다. 고쳐서 같은 이름으로 다시 넣어 처리에 성공하면 메모는 자동으로 지워집니다.
- 워드·엑셀의 잠금 파일(`~$…`), `Thumbs.db`, `desktop.ini`, `.DS_Store`, 바로가기(`.lnk`), 숨김/시스템 파일, 임시 파일(`.tmp` 등)과 위 메모는 **조용히 무시**합니다(`_rejected`로 보내지 않음).
- 다른 프로그램이 계속 잡고 있는 파일은 기본 60회 연속 스캔(약 5분, `WIKI_LOCKED_MAX_SCANS`)까지 기다렸다가 포기하고 `_failed` 로 옮기며 '파일을 읽을 권한이 없거나 다른 프로그램이 계속 사용 중입니다' 메모를 남깁니다. 짧게 잠긴 경우는 실패로 세지 않습니다.
- 바로가기·연결 폴더(심볼릭 링크/정션)는 다른 부서 폴더를 가리킬 수 있어 **처리하지 않고** 관리자 로그에 남깁니다.

**관리자가 하는 일**
- `inbox` 바로 아래(부서 폴더 밖)에 놓인 파일은 `_rejected\`로 옮겨지고 `.reason.txt`가 붙습니다. 루트에는 메모를 쓰지 않습니다(파일 이름이 모두에게 보이므로). 관리자가 주인을 확인해 올바른 부서 폴더로 옮겨 주세요. 현황은 doctor `inbox.layout` 이 개수만 알려 줍니다.

- **`_rejected\`, `_failed\`, `_done\` 는 관리자 전용**입니다. 여러 부서의 파일 이름과 사유가 섞여 있으므로 직원에게 읽기 권한을 주면 안 됩니다(위 레시피대로면 ABE 로 보이지 않음). `inbox` 바로 아래 `_` 로 시작하는 폴더(대소문자 무관, `_Done` 포함)는 모두 예약되어 조용히 건너뜁니다.
- **조용히 무시되는 이름** — 아래에 해당하는 파일은 정상 파일이어도 **절대 처리되지 않고 알림도 없습니다**. 직원에게 알려 주세요: `~$` 로 시작, `.` 으로 시작, `.tmp` `.part` `.partial` `.crdownload` `.swp` `.lnk` 로 끝남, `Thumbs.db` `desktop.ini`, `.처리결과.txt` 메모, 숨김/시스템 속성 파일. 파일 이름은 200자 이하, 폴더는 `inbox` 아래 6단계까지만 봅니다(더 깊으면 메모만 남기고 들어가지 않음).
- **알려진 한계(미해결)**: (1) 연결 폴더 검사와 실제 읽기 사이의 짧은 틈(TOCTOU)이 남아 있습니다. 링크를 만들려면 Windows 권한(SeCreateSymbolicLink / 폴더 쓰기)이 필요하므로 NTFS 권한으로 완화합니다. (2) 폴더당 파일 수·큐 길이 상한이 아직 없습니다. 한 사람이 수천 개를 한꺼번에 넣으면 처리가 순차라서 다른 부서가 지연될 수 있습니다.

**왜 "모두가 쓰는 폴더 하나"는 지원하지 않는가**: space가 곧 열람 권한(ACL)인데, 한 폴더에 모인 파일의 소유자(작성자)로 부서를 정하는 것은 신뢰할 수 없습니다(복사·이동·대리 저장 시 소유자가 바뀜). 내용이나 AI로 부서를 추측하면 다른 부서 문서가 노출될 수 있어 막아 두었습니다.

**폴더 별칭(한글 폴더 이름)**: `WIKI_INBOX_ALIASES=C:\wiki\config\inbox-aliases.json` (파일 형식은 `config/env.example` [8]).
```json
{ "인사팀": "dept-hr", "인프라팀": "dept-a", "인프라팀/당직": "dept-a/part-1" }
```
- 폴더 경로에서 **가장 긴 별칭이 우선**이고, **별칭 폴더 아래 하위 폴더는 그 별칭의 space 를 그대로 물려받습니다**(최대 4단계). 하위 폴더를 다른 space 로 좁히려면 그 폴더의 별칭을 하나 더 추가하세요.
  예: 위 파일이면 `인프라팀\2026\a.md` -> `dept-a`, `인프라팀\당직\b.md` -> `dept-a/part-1`, `인프라팀\당직\야간\c.md` -> `dept-a/part-1`. 하위 폴더 이름만으로 새 하위 space 가 생기지는 않습니다. 별칭이 없는 폴더도 정식 space 이름(`dept-a`)이면 그대로 동작하고, 나머지는 예전처럼 거부됩니다.
- 한글 폴더 이름은 NFC/NFD(맥 등에서 자모가 분리되어 올 수 있음)와 대·소문자를 구분하지 않고 비교합니다(Windows 폴더가 대소문자를 구분하지 않으므로).
- 파일에 문제가 하나라도 있으면 **파이프라인이 시작을 거부**합니다(잘못된 부서로 들어가는 것보다 낫습니다): 빈 키, `..`, `\`, `:`, `_`로 시작하는 단계, Windows 예약어(`con` 등), 끝의 점·공백, 대소문자/정규화만 다른 중복 키, 올바르지 않은 space 값, 64KiB 초과, 그리고 다른 부서의 정식 space 폴더(`dept-b` 등)를 다른 space 로 돌리는 키.
- 이 때문에 `HR` 처럼 영문 소문자로 읽혀 정식 space 이름과 겹치는 키는 쓸 수 없습니다(Windows 는 `HR`/`hr` 을 같은 폴더로 보므로, 그 폴더에 쓸 수 있는 사람의 파일이 정식 부서 `hr` 이 아닌 다른 space 로 들어가는 것을 막기 위함). 한글이나 `인사-HR팀` 처럼 구분되는 이름을 쓰세요.
- 파일은 이후 모든 곳(`raw/`, `wiki/`, `_done/_failed/_rejected`)에 **정식 space 이름** 기준으로 저장됩니다.

## 4. 자료 유형별 입력 요령

위키 문서는 LLM이 입력 글을 읽고 정리합니다. 아래 요령은 *경험칙*이며 이 효과를 따로 측정하지는 않았습니다(**[미검증]**). 다만 "사실이 글에 분명히 적혀 있을수록 답변이 정확하다"는 점은 평가에서 확인했습니다(숫자·날짜·고유명사가 본문에 그대로 있어야 합니다).

| 자료 | 권장 방식 | 피할 것 |
|---|---|---|
| 회의록 | 제목에 날짜(`주간회의록 2026-09-30`), 결정사항·담당자·기한을 줄 단위로 | 사진·캡처만 붙인 문서(글자가 없으면 읽을 수 없음) |
| 문제 리스트·조치 | 표로: 번호 / 문제 / 원인 / 조치 / 결과 / 담당 / 일자 | 한 칸에 여러 사건을 몰아 쓰기 |
| 장애·사고 보고 | 발생일·시스템·증상·원인·조치·복구시간(분)을 각각 적기 | "금일 장애 건" 처럼 날짜·대상이 없는 제목 |
| 메일 | `.eml`로 저장. 스레드(답장 묶음)는 가장 마지막 메일 1통에 이전 내용이 인용된 형태도 가능 | `.msg` 그대로 올리기(미지원) |
| 엑셀 양식 | 표 **머리글을 첫 표 행**에, 작성일·작성자 같은 메타 행은 표 *위*에 | 숨김 시트·병합이 지나치게 복잡한 한 장짜리 다중 양식 |
| 워드 양식 | 표 첫 행에 항목명, 결재란은 별도 표로 | 표를 이미지로 붙이기 |
| 정정·변경 | "정정 메모" 문서를 새로 넣기(5절) | 기존 위키 문서를 직접 수정 |

### 4-1. 메일을 `.eml`로 저장하는 법 **[미검증: 사내 메일 클라이언트별 메뉴는 확인하지 못함]**
- Gmail: 메일 열기 → ⋮ → "원본 보기" → "원본 다운로드" → `.eml`.
- Thunderbird: 메일 → 파일 → 다른 이름으로 저장 → 파일(.eml).
- Outlook: 버전에 따라 `.msg`로만 저장되는 경우가 있습니다. `.eml`로 내보내는 방법은 사내 IT 안내를 따르세요. `.msg`는 지원하지 않습니다.

## 5. 틀린 내용 고치기 (옵시디언에서 직접 고치지 마세요)

위키 문서는 새 자료가 들어올 때 LLM이 다시 쓰며 **덮어씁니다**(이전 버전은 `.md.bak` 한 개만 보관). 그러므로:
1. 원본 자료가 틀렸다면 → 원본을 고쳐서 같은 부서에 다시 넣으세요(새 raw 사본이 만들어지고, LLM이 `Update`/`Disputed`로 반영).
2. 기존 결정이 바뀌었다면 → `# 정정 메모 2026-10-05`처럼 *무엇이 어떻게 바뀌었는지*를 한 장으로 적어 넣으세요. 기존 내용과 충돌하면 문서에 `Disputed` 표시가 남습니다.
3. 위키 문서의 `sources`/`related`/`title` 머리말(frontmatter)을 직접 수정하지 마세요. 권한 판단과 갱신 로직이 이 정보를 참고합니다.
4. **충돌 표시 보기**: 질문 답변의 인용 버튼 앞에 **⚠** 가 붙은 문서는 출처끼리 내용이 다르다는 뜻입니다(문서 끝의 `## Disputed` 절 확인). 관리자는 `python -m llmwiki.lint_admin disputed` 로 충돌 문서 전체 목록을 볼 수 있습니다(부서 구분 없이 나오므로 관리자만 실행). 충돌은 올바른 원본을 확인한 뒤 위 1·2번 방법으로 정리합니다. **[검증: 자동 테스트]** 대체되어 낡은 내용(`Outdated`)의 자동 표시는 아직 없습니다.
   - **새 소식 탭**: 내가 볼 수 있는 문서 중 최근 바뀐 문서를 날짜순으로 보여 줍니다(제목·날짜만, 클릭하면 문서). **[검증: 자동 테스트(권한 누수 포함)]**
   - **지식 공백**: 관리자는 `python -m llmwiki.lint_admin gaps` 로 "근거 없음"으로 끝난 질문을 많이 나온 순으로 볼 수 있습니다(= 위키에 없는 지식, 질문 원문이 보이므로 관리자만 실행). `python -m llmwiki.lint_admin stats` 는 질문 수·근거 없음 수·사용자 수·피드백 수를 보여 줍니다.
5. **답변 피드백**: 답변 아래 **👍 도움됨 / 👎 틀림·부족** 버튼으로 의견을 남길 수 있습니다. 기록되는 것은 평가와 인용된 문서 경로뿐이며 질문·답변 내용은 저장하지 않습니다. 관리자는 `python -m llmwiki.lint_admin feedback` 으로 문서별 👎/👍 횟수를 (👎 많은 순) 볼 수 있고, 👎 가 많은 문서는 원본을 확인해 위 1·2번으로 고칩니다. **[검증: 자동 테스트]**

## 6. 자연어 입력창은 어떻게 위키 자료와 연결되는가

### 6-1. 질문 1건이 처리되는 과정 **[검증: 코드 확인 + 실제 모델 테스트]**
```
[질문 탭] "저장 공간이 가득 차서 시스템이 멈춘 적 있어?"
   │ ① 로그인한 사용자와 그 사용자의 부서(space) 확인
   ▼
   ② 이 사용자가 읽을 수 있는 문서만 후보로 추림  ← 권한 필터가 검색보다 먼저.
   │    (권한 없는 문서는 검색 점수·순위·답변 어디에도 영향을 주지 않음)
   ▼
   ③ 두 가지 검색을 합침
   │    - 키워드 검색(BM25): 질문의 단어가 문서에 있는지
   │    - 의미 검색(bge-m3 임베딩): 표현이 달라도 뜻이 비슷한 문서 ("저장 공간이 가득" ↔ "디스크 용량 부족")
   │    → 상위 K개 문서 선택(기본 5개)
   ▼
   ④ 선택한 문서 내용에 번호를 붙여 LLM에 전달 (모델 컨텍스트 한도에 맞춰 길이 조정)
   ▼
   ⑤ LLM이 *그 문서에 있는 내용만* 근거로 답변. 없으면 정확히 "근거 없음"
   ▼
   ⑥ 답변 + 출처 번호 [1] [2] 표시 → 번호를 누르면 해당 위키 문서가 열림
   ▼
   ⑦ 누가 무엇을 물었는지 감사 기록(질문 원문은 기록되지만 답변·문서 내용은 기록하지 않음)
```
- 후보 문서가 **하나도 없으면 LLM을 부르지 않고** 즉시 "근거 없음"을 돌려줍니다.
- 질문은 **매번 독립적**입니다(이전 대화를 기억하지 않음). 후속 질문에는 앞 질문의 핵심어를 다시 넣어 주세요.
- 질문 길이는 2,000자까지입니다.
- 실제 모델(`gemma-4-e4b` + `bge-m3`)로 확인한 예 **[검증]**: "저장 공간이 가득 차서 시스템이 멈춘 적 있어?" → 키워드 검색은 단어가 달라 0건, 의미 검색이 "디스크 용량 부족" 장애 보고서를 1위로 찾아 `디스크 용량 부족(사용률 98%)` + 출처와 함께 답변. 다른 부서 문서를 묻는 질문은 "근거 없음".
- **브라우저에서 직접 확인한 흐름 [검증, 2026-10-02]** (개발용 로그인, 소형 모델):
  1. 로그인 화면(사용자 ID 입력) → 로그인 → 상단에 **질문 / 문서 / 업로드** 탭과 로그아웃 버튼.
  2. 질문창에 "저장 공간이 가득 차서 로그 서버가 멈춘 장애는 언제 복구됐고 얼마나 걸렸어?" 입력 → 약 30초 뒤 답변 `log-srv-02 디스크 용량 부족 장애는 2026-05-21에 복구, 소요 시간 2시간 10분 [1]`과 출처 버튼 `[1] 장애 보고서: log-srv-02 디스크 용량 부족 (2026-05-21)`. (질문에는 "디스크"가 없고 문서에는 "저장 공간"이 없는데도 찾음 = 의미 검색.)
  3. 출처 버튼을 누르면 주소가 `#/article/<주제>/<문서>.md`로 바뀌며 문서 전문이 열림(경로와 갱신일 표시).
  4. **권한**: A팀 계정으로 B팀 문서 주소를 직접 입력하면 "문서를 찾을 수 없습니다." 같은 주소를 두 부서 권한이 모두 있는 계정으로 열면 문서가 보임 → "찾을 수 없음"은 권한 때문이며, 문서가 존재하는지도 알려 주지 않음.
  - 직접 확인하지 못한 화면: **업로드 탭 조작**, **문서 탭의 목록**, 이미지 스크린샷(렌더링 지연으로 텍스트 구조로만 확인).

|---|---|---|---|

### 6-3. 연결 확인 (처음 한 번) **[검증: 명령은 개발 PC에서 실행, Gauss는 미확인]**
1. `python -m llmwiki.doctor` — LLM·임베딩 연결, 인증 오류, 컨텍스트 크기, 파서 자체 시험을 점검해 한국어로 알려줍니다.
2. 자료를 몇 건 넣고(3절) 파이프라인이 처리할 때까지 기다린 뒤, `wiki/_meta/<부서>/log.md`에 `ingest | New …` 줄이 생겼는지 확인.
3. 웹 질문 탭에서 자료에 *분명히 있는 내용*을 물어 출처와 함께 답이 나오는지 확인.
4. 자료에 *없는 내용*과 *다른 부서 내용*을 물어 "근거 없음"이 나오는지 확인(권한 시험).
5. 이미 위키가 있는데 의미 검색이 안 되면(임베딩이 비어 있음): `python -m llmwiki.engine.reindex`

### 6-5. 질문 잘 하는 법
- 시스템·날짜·대상을 넣으세요: "log-srv-02 디스크 장애는 언제 복구됐나요?" (O) / "그 장애 어떻게 됐어?" (X)
- 한 번에 한 가지만 물으세요. 표현은 달라도 됩니다(의미 검색). 숫자·날짜는 **출처 문서를 눌러 확인**하세요.
- **후속 질문**: 바로 앞 질문을 이어 "그건 얼마야?"처럼 물을 수 있습니다(최근 3번의 질문·답변만 참고하며, 서버에 저장하지 않고 브라우저에만 있습니다). 이전 답변은 **근거가 아니라 지시어 해석용**이라, 답은 항상 위키 문서에서만 나옵니다. 주제를 바꿀 때는 **새 대화** 버튼을 누르세요. **[검증: 자동 테스트(누수 포함), 실제 모델의 후속 질문 이해도는 미검증]**
- "근거 없음"이 나오면: 자료가 안 들어갔거나(`log.md` 확인), 권한이 없거나, 질문이 너무 모호하거나, 임베딩이 비어 있는 경우입니다(위 6-3의 reindex).

### 6-6. 이상할 때
| 증상 | 원인 후보 | 조치 |
|---|---|---|
| 항상 "근거 없음" | 자료가 처리되지 않음 / 권한 부서가 다름 | `_failed`·`_rejected`의 `.reason.txt`, `log.md`, 로그인 계정의 부서 확인 |
| 표현을 바꾸면 못 찾음 | 임베딩 생성 실패(LM Studio 꺼짐, 임베딩 모델 컨텍스트 부족) | LM Studio 실행·모델 로드 확인, 컨텍스트 길이 확대 후 `reindex` |
| 답이 틀림 | 원본이 틀렸거나, 문서가 여러 개라 섞임 | 출처 번호의 문서와 raw 확인 → 5절 방식으로 정정 |
| 응답이 느림 | 모델이 큼/추론 모델 | `WIKI_LLM_STREAM=1`, `WIKI_LLM_TIMEOUT` 증가 |
| 화면에 "답변 서버에 연결할 수 없습니다"(502 `llm_unavailable`) | LLM 서버 연결·인증 실패, 또는 **LM Studio에 요청이 동시에 몰림** | `python -m llmwiki.doctor`. 잠시 뒤 다시 질문. 반복되면 아래 참고 |
- **LM Studio는 여러 요청을 동시에 처리하는 데 약합니다 [검증].** 개발 PC에서 한 모델에 평가·웹 질문·진단 스크립트가 겹치자 웹 질문이 22초 뒤 "답변 서버에 연결할 수 없습니다"로 실패했고, 같은 시간대 평가 하나가 `HTTP 400`으로 실패했습니다. 조용해진 뒤 같은 질문은 정상 답변했습니다. 그래서 **사내 80명 운영의 답변 모델은 Gauss**가 맡고, 같은 PC의 LM Studio는 *임베딩(bge-m3) 전용*으로 쓰는 구성을 권장합니다(임베딩은 질문당 1회, 짧은 호출).
- 서버 로그에는 보안상 원인 상세를 남기지 않고 `llm unavailable`만 남습니다. 원인을 보려면 `python -m llmwiki.doctor`를 쓰세요.

## 7. 알려진 한계 (정직한 목록)

1. **옵시디언 부서별 내보내기 없음**: `wiki/`는 전 부서가 섞여 있어, 옵시디언은 관리자 전용입니다. 일반 사용자용 읽기 전용 사본이 필요하면 별도 개발이 필요합니다.
2. **엑셀·워드 표 머리글 판별 [수정 완료, 2026-10-02]**: 표 위에 "작성일/작성자" 같은 메타 행이 있는 양식에서 메타 행을 머리글로 잘못 잡던 문제를 고쳤습니다. 이제 메타 행은 표 *위의 한 줄*(`작성일: 2026-10-01 · 작성자: 김서연`)로 분리되고 진짜 머리글이 표 머리글이 됩니다. 평가용 병합 셀 양식 19개로 확인했습니다. **주의: 수정 *이전*에 만든 위키 문서는 고쳐지지 않으므로, 이미 입력한 양식 문서가 있다면 원본을 다시 넣어 갱신하세요.** 남은 한계: 항목명·값만 있는 신청서 같은 양식은 `열 1…4`처럼 번호 머리글 표로 나옵니다(내용은 모두 보존). 머리글이 날짜인 표(일자별 열)도 번호 머리글로 나옵니다.
3. **하이브리드 검색은 스스로 거절하지 못함**: 거절은 LLM의 "근거 없음"에 의존합니다(`docs/RAG-TUNING-REPORT.md`).
4. **스캔 PDF·한글(HWP)·구형 Office·`.msg` 미지원**(OCR은 사내에서 연결).
5. **옵시디언·웹 화면의 실제 조작 화면은 이 개발 PC에서 사람이 눈으로 확인하지 못한 부분이 있습니다.** 확인한 범위는 아래 변경 이력에 적습니다.
6. 위키 변경 이력(git)·관리자 화면·자동 백업은 아직 없습니다.
